# Регламент разработки проекта

Шаблон регламента для автоматической проверки качества кода 1С.

Значения в шаблоне — образец: префикс `ДРБ_`, фамилия «Иванов И.И.», формат
номера задачи. Замените их требованиями своего проекта.

Файл читают двое: разработчик — как обычный документ, и программа
«1С: AI инструменты» — как набор правил. Программе адресованы только
огороженные блоки с пометкой `правило`; весь остальной текст — пояснение
для человека, и оно же попадает в отчёт как формулировка замечания.

## Область применения

Регламент устанавливает правила редактирования типового решения на платформе
1С:Предприятие и обязателен для всех разработчиков проекта. Цели
стандартизации:

* повышение качества программного кода — логика читается, ошибка находится,
  новый разработчик входит в проект быстрее;
* применение рекомендаций фирмы «1С» и практик сообщества разработчиков;
* упрощение установки новых релизов типовых решений;
* недопущение типовых ошибок на всех этапах разработки и сопровождения
  доработанного решения.

Соблюдение регламента снижает затраты на сопровождение доработок и делает
приёмку задачи предсказуемой: единый стиль и порядок работы означают, что
код проходит приёмку без переделок.

Порядок работы разработчика — своя база для разработки, захват объектов,
передача дел при отсутствии — здесь не описан: это организация работы,
а не требование к коду.

## Как править этот файл

* **Правило — это блок.** Заголовок раздела над блоком становится ссылкой
  на пункт регламента в отчёте, абзац перед блоком — текстом замечания.
* **Списки внутри правила не ограничены.** Дописанная строка в таблице
  запрещённых методов, в перечне областей или в пределах начинает работать
  сразу: алгоритм проверки один и тот же, а состав правил — проектный.
* **Уровень** пишется по-русски: `критично`, `высокий`, `средний`, `низкий`,
  `информация`.
* **Правило снимается** строкой `выключено: да` — раздел при этом остаётся
  на месте вместе с пояснением.
* **Решётка** начинает комментарий только в начале строки: внутри значений
  она часть маски номера задачи.
* Код правила берётся из перечня, который понимает программа. Неизвестный код
  прогон не рвёт: правило пропускается, а отчёт называет его отдельной
  строкой — «в регламенте есть, программой не проверяется».
* **Раздел без блока `правило` проверяется на код-ревью.** Требование от этого
  не слабее: программа просто не берётся судить о том, чего не видит в коде.

## 1. Общие параметры

Проектный префикс доработок — `ДРБ_`: `бит` обозначает компанию,
`п` — офис. Регламент дополняет встроенные проверки программы: замечания
стандартов 1С остаются в отчёте наравне с проектными.
Значение `заменяет` оставило бы в отчёте только правила этого файла.

```регламент
название: Регламент разработки проекта
версия: 1.0
режим: дополняет
префикс доработок: ДРБ_
```

## 2. Где выполняются доработки

### 2.1. Основная конфигурация и расширение

В основную конфигурацию добавляются только **новые объекты метаданных**:
объекты, реквизиты, общие модули и тому подобное. Все остальные доработки
выполняются в расширении. Если реализовать функционал в расширении
не получается, реализация в основной конфигурации согласуется с техническим
архитектором проекта до начала работы, а не после неё.

Типовой код в конфигурации не правится: изменение типовой процедуры — это
всегда расширение.

### 2.2. Аннотации расширения

Порядок выбора аннотации — от наименее навязчивой к наиболее навязчивой:

* **`&После`** — предпочтительный способ. Если задача решается им, берётся он.
* **`&Вместо` вместе с `ПродолжитьВызов()`** — когда меняется начало типовой
  процедуры, а дальше вызов возвращается в типовую.
* **`&Вместо` без продолжения** — только когда типовая процедура заменяется
  полностью.
* **`&ИзменениеИКонтроль`** — когда изменяется середина типовой процедуры
  и другого способа нет. Если задача решается через `&После` либо через
  `&Вместо` с `ПродолжитьВызов()`, `&ИзменениеИКонтроль` не используется:
  такая аннотация ломается при каждом обновлении типовой процедуры.

Копировать типовую процедуру в расширение целиком ради правки нескольких
строк нельзя: при обновлении копия останется прежней, а типовая процедура
уйдёт вперёд. Замечанием считается ровно один случай — метод с аннотацией
замены, который **ни разу не зовёт** `ПродолжитьВызов()`. Вызов ищется
внутри самого метода: `ПродолжитьВызов()` в комментарии или в соседнем
методе возвратом управления не является.

```правило
код: policy.extension-annotations
уровень: средний
аннотация замены: &Вместо
вызов продолжения: ПродолжитьВызов
```

### 2.3. Печатные формы, отчёты и обработки

Доработка типовой печатной формы, типового отчёта или типовой обработки
делается в расширении. Сами типовые объекты не дорабатываются.

### 2.4. Возможность изменения типовых объектов

Когда изменение типового объекта всё же необходимо, возможность изменения
с сохранением поддержки включается **точечно** — для того объекта, который
меняется: для конкретной табличной части, конкретного реквизита. Включать
её рекурсивно на весь объект нельзя: снятая с поддержки ветка метаданных
перестаёт обновляться вместе с релизом.

### 2.5. Программная модификация форм

Реквизиты и элементы на форму типового объекта добавляются **программно**,
в расширении `ДРБ_Дополнения`, в модулях форм объектов, в обработчике
`ПриСозданииНаСервере`. Для этого в расширении есть общий модуль
`ДРБ_ПрограммнаяМодификацияФорм` с функциями добавления реквизитов
и элементов формы и установки действий.

Интерактивное изменение формы допускается только для новых объектов,
добавленных (а не заимствованных) в расширение.

## 3. Именование объектов конфигурации

### 3.1. Префикс доработок

Все добавляемые объекты верхнего уровня именуются с проектным префиксом:
справочники, документы, регистры, общие модули, подсистемы, обработки, отчёты,
подписки на события, роли. Реквизиты, табличные части и предопределённые
элементы объекта, который уже имеет префикс, префикса не требуют.

Требование относится к объектам **конфигурации**, добавленным по отношению
к конфигурации поставщика. Объекты, добавленные в расширение, именуются
с префиксом самого расширения, поэтому
проектного префикса доработок от них не требуется и замечанием их отсутствие
не считается.

```правило
код: policy.name-prefix
уровень: высокий
префикс: ДРБ_
```

### 3.2. Синоним роли

В конец синонима роли добавляется признак проекта — по нему проектную роль
видно в списке прав рядом с типовыми.

```правило
код: policy.role-synonym-suffix
уровень: низкий
суффикс синонима роли: (ДРБ)
```

## 4. Требования к новым объектам

Новый документ подключается к стандартным механизмам платформы и БСП:
печати, версионированию, а также получает стандартные отчёты «Связанные
документы» и «Движения документа». Документ, у которого этого нет,
у пользователя ведёт себя не так, как остальные документы базы.

Подключение к печати видно в модуле менеджера — там регистрируются команды
печати; версионирование и стандартные отчёты проверяются на код-ревью.

```правило
код: policy.manager-procedures
уровень: средний
обязательные процедуры:
  - Документ -> ДобавитьКомандыПечати
```

## 5. Комментирование изменений

### 5.1. Формат пометки

Изменение типового кода отмечается пометкой разработчика. В пометке — префикс,
фамилия с инициалами, дата и номер задачи.

```text
// ++ ДРБ_Иванов И.И. 01.05.2026 ПРО-78 Заполнение проектных данных
// ++ ДРБ_Иванов И.И. 01.05.2026 #0001234 Заполнение проектных данных
```

**Вид пометки проверяется строго.** «//++», «// ++Фамилия», «// +» —
это отдельное замечание: по единому виду пометку находят поиском по всем
модулям, а разнобой из такого поиска выпадает. Пометки вендора и платформы
(«//++ НЕ УТ», «// Начало СтандартныеПодсистемы…») регламентом не судятся:
это условная сборка типового решения, а не правка разработчика.

**Формат номера задачи задан маской** (см. пункт 6). Программа различает два
разных нарушения и пишет о них по-отдельности: номера задачи в пометке нет
вовсе — и номер есть, но записан не по формату проекта. Первое означает, что
правку не связать с требованием; второе — что связать её можно только руками.

```правило
код: policy.change-marker
уровень: средний
открывающая пометка: // ++
состав: префикс, фамилия и инициалы, дата, номер задачи
маска номера задачи: (?:[#№]\s*)?(?:[A-Za-zА-Яа-я]{2,10}-\d{1,6}|\d{4,7})
пример номера задачи: ПРО-78 либо #0001234
```

### 5.2. Закрывающая пометка

На этом проекте закрывающая пометка **в конце метода** не используется: у новой и изменённой процедуры остаётся только открывающая
пометка перед объявлением. Запрет действует на строке `КонецПроцедуры`
либо `КонецФункции` и на следующей за ней строке — именно там её обычно
и ставят по привычке.

Внутри тела метода закрывающая пометка допустима: там она обозначает границу
вставленного блока, и без неё не видно, где правка заканчивается. Это
проектное решение: там, где принят полный формат — с парной пометкой после
метода, — значение меняется на `обязательна`.

```правило
код: policy.change-marker-closing
уровень: низкий
закрывающая пометка: запрещена
```

## 6. Помещение в хранилище

Комментарий помещения содержит номер задачи. По нему восстанавливают,
зачем сделана каждая правка. Любые дополнительные пояснения в комментарии —
по желанию разработчика.

```text
ПРО-78 Краткое название задачи
#0001234 Краткое название задачи
```

**Маска задаёт формат номера, и значок к нему не привязан**: маска ниже
принимает и ключ задачи вида «ПРО-78», и номер со значком, и номер без него. Как
и в пометке изменения, «номера нет» и «номер не по формату» — разные
замечания. Служебные комментарии платформы («Создание хранилища
конфигурации») номера задачи не требуют и замечанием не считаются.

```правило
код: policy.commit-ticket
уровень: средний
маска номера задачи: (?:[#№]\s*)?(?:[A-Za-zА-Яа-я]{2,10}-\d{1,6}|\d{4,7})
пример номера задачи: ПРО-78 либо #0001234
```

## 7. Структура модулей

### 7.1. Области модуля

Код размещается в стандартных областях — тех же, что перечислены в стандарте
ИТС 455 «Структура модуля» (`https://its.1c.ru/db/v8std/content/455/hdoc`):
`ОписаниеПеременных`, `ПрограммныйИнтерфейс`,
`СлужебныйПрограммныйИнтерфейс`, `СлужебныеПроцедурыИФункции`,
`ОбработчикиСобытий`, `ОбработчикиСобытийФормы`,
`ОбработчикиСобытийЭлементовШапкиФормы`,
`ОбработчикиСобытийЭлементовТаблицыФормы<ИмяТаблицы>`,
`ОбработчикиКомандФормы`, `ДляВызоваИзДругихПодсистем`,
`ОбновлениеИнформационнойБазы`, `Инициализация`.

**Собственные области разработчику не запрещены**: требование в том, чтобы
стандартные области были на месте и код лежал в них, а не в том, чтобы других
областей в модуле не было.

В модулях объекта, менеджера и форм расширения области обязательны так же,
как в конфигурации. Заимствованная типовая процедура кладётся в **ту же**
область, в которой она лежит в модуле конфигурации, а если в конфигурации
эта область вложена в другие, **иерархия областей переносится в расширение
целиком**, вплоть до верхнеуровневой.

Удобно держать рядом файл шаблонов стандартных областей для конфигуратора:
области вставляются из него, а не набираются руками.

```правило
код: policy.module-regions
уровень: средний
обязательные области:
  - общий модуль -> ПрограммныйИнтерфейс
  - модуль формы -> ОбработчикиСобытийФормы
```

### 7.2. Область собственного метода расширения

Собственному методу расширения область выбирает регламент: экспортный
кладётся в `ПрограммныйИнтерфейс`, неэкспортный — в
`СлужебныеПроцедурыИФункции`. На заимствованные методы правило
не распространяется: они лежат там же, где лежат в модуле конфигурации.

```правило
код: policy.own-routine-region
уровень: низкий
области собственных методов:
  - экспортный -> ПрограммныйИнтерфейс
  - неэкспортный -> СлужебныеПроцедурыИФункции
```

### 7.3. Пустые области

Пустая область — след незаконченной правки: её переносят вместе с иерархией
заимствованной процедуры и оставляют, когда код из неё убран. В расширении
пустых областей быть не должно.

```правило
код: policy.empty-regions
уровень: низкий
пустые области: запрещены
```

### 7.4. Область добавленного функционала

В основной конфигурации новые процедуры и функции типового модуля собираются
в отдельной области в конце модуля: так их видно и они не мешают обновлению.
В расширении эта область не используется — собственные методы размещаются
в стандартных областях, а иерархия областей заимствованной типовой процедуры
переносится полностью.

```правило
код: policy.added-code-region
уровень: средний
область добавленного кода: ДРБ_ДобавленныйФункционал
область добавленного кода в расширении: запрещена
```

### 7.5. Инструкция препроцессора в модулях расширения

В модулях объекта, менеджера и команды расширения первой строкой идёт
инструкция препроцессора: без неё модуль компилируется в клиентском контексте.

```правило
код: policy.extension-guard
уровень: низкий
первая строка: #Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда
виды модулей:
  - модуль объекта
  - модуль менеджера
  - модуль команды
```

## 8. Методы, которые использовать нельзя

Устаревшие методы платформы заменяются актуальными. Список проектный: строка
«что использовать нельзя -> чем заменить» добавляется по мере того, как метод
признаётся устаревшим на проекте. Обращение через точку (`Массив.Найти(…)`)
замечанием не считается — это метод коллекции, а не метод платформы.

Два случая, которые встречаются чаще прочих:

```text
// нельзя                                    // нужно
Найти(ИмяФайла, НачалоИмениФайла)            СтрНайти(ИмяФайла, НачалоИмениФайла)
ДатаФайла < ТекущаяДата() - 86400            ДатаФайла < ТекущаяДатаСеанса() - 86400
```

Почему это важно, а не «просто устарело»:

* **`ТекущаяДата()`** (стандарт ИТС 643 «Работа в разных часовых поясах»)
  возвращает дату и время СЕРВЕРНОГО компьютера. Если часовой пояс сервера
  не совпадает с часовым поясом пользователей, документы и записи получают
  чужое время, а вычисленное на клиенте и на сервере время расходится.
  На сервере — `ТекущаяДатаСеанса()`; для отметки, не зависящей от часового
  пояса, — `УниверсальноеВремя()`; на клиенте дата берётся с сервера либо
  из самого документа.
* **`Сообщить()`** не позволяет привязать сообщение к реквизиту формы
  и ведёт себя непредсказуемо в фоновых заданиях. Замена —
  `СообщениеПользователю` с указанием поля и ключа данных.
* **Модальные и синхронные вызовы** (`Предупреждение`, `Вопрос`,
  `ОткрытьФормуМодально`, ввод значений) не поддерживаются веб-клиентом
  и мобильным клиентом, а при режиме «Использовать модальность: не
  использовать» приводят к ошибке во время работы. Замена — асинхронные
  методы с оповещением о завершении.

Эти же методы проверяет и встроенное правило программы. **Замечание при этом
одно**: когда регламент включён, о методе говорит регламент — с уровнем
проекта и ссылкой на этот пункт, — а встроенное правило молчит, чтобы
не показывать одно и то же дважды.

```правило
код: policy.forbidden-methods
уровень: средний
замены:
  - Найти -> СтрНайти
  - ТекущаяДата -> ТекущаяДатаСеанса
  - ПолучитьФорму -> ОткрытьФорму
  - Сообщить -> СообщениеПользователю
  - ОткрытьФормуМодально -> ОткрытьФорму с оповещением
  - Предупреждение -> ПоказатьПредупреждение
  - Вопрос -> ПоказатьВопрос
  - ОткрытьЗначение -> ПоказатьЗначение
  - ВвестиЧисло -> ПоказатьВводЧисла
  - ВвестиСтроку -> ПоказатьВводСтроки
  - ВвестиДату -> ПоказатьВводДаты
  - ВвестиЗначение -> ПоказатьВводЗначения
```

## 9. Записи, запрещённые в коде

Требования, которые проверяются по самой записи в тексте модуля. Слева — что
искать, справа — что сказать разработчику. Запись ищется подстрокой; запись,
взятая в косые черты, — регулярным выражением.

Аннотации `&Вместо` в этом перечне нет намеренно: сама по себе она разрешена,
а копию типовой процедуры находит правило из пункта 2.2.

```правило
код: policy.forbidden-text
уровень: средний
записи:
  - /Пароль\s*=\s*"[^"]+"/ -> Пароль не хранится в коде: используйте безопасное хранилище
```

## 10. Пределы

Значения, за которыми код перестаёт читаться. Меняются от проекта к проекту:
достаточно поправить число или дописать строку.

Запрос длиннее ста строк в теле процедуры не оставляется: текст запроса
выносится в отдельную функцию, которая его возвращает.

```правило
код: policy.limits
уровень: низкий
пределы:
  - строк в запросе -> 100
  - строк в процедуре -> 200
  - параметров у метода -> 7
  - глубина вложенности -> 5
```

## 11. Оформление кода

Тексты модулей пишутся на русском языке, на одной строке размещается один
оператор, для отступов используется табуляция.

```правило
код: policy.formatting
уровень: низкий
требования:
  - отступ табуляцией
  - один оператор в строке
  - язык имён: русский
```

### 11.1. Имена переменных

Имя переменной пишется словом, а не аббревиатурой: `км`, `пк`, `пв` понятны
только тому, кто писал этот код, и то до конца недели. Мерилом служит длина
имени; имена, которые на проекте приняты короткими, перечисляются рядом.

```text
// нельзя                                    // нужно
км = Новый КомпоновщикМакетаКомпоновкиДанных;   КомпоновщикМакета = Новый КомпоновщикМакетаКомпоновкиДанных;
пк = Новый ПроцессорКомпоновкиДанных;           ПроцессорКомпоновки = Новый ПроцессорКомпоновкиДанных;
```

```правило
код: policy.short-names
уровень: низкий
минимальная длина имени: 3
разрешённые имена: Ном, Стр
```

## 12. Встроенные проверки программы

Проверки, которые программа выполняет всегда. Здесь им назначается уровень,
принятый на проекте; строка `выключено: да` снимает проверку.

### 12.1. Транзакции

Начало и завершение транзакции сбалансированы, транзакция защищена обработкой
исключения.

```правило
код: std.transaction-without-try
уровень: высокий
```

### 12.2. Обработка исключений

Перехваченное исключение записывается в журнал регистрации либо пробрасывается
дальше: иначе причина сбоя теряется.

```правило
код: std.catch-without-log
уровень: средний
```

### 12.3. Модальность и синхронные вызовы

Модальные окна и синхронные вызовы без обоснованной необходимости
не используются.

```правило
код: std.deprecated-sync-call
уровень: высокий
```

### 12.4. Подписки на события

У каждой подписки есть существующий обработчик: подписка с потерянным
обработчиком даёт ошибку у пользователя при первом же событии.

```правило
код: std.subscription-without-handler
уровень: высокий
```

### 12.5. Циклическая вставка коллекции

Коллекция не вставляется сама в себя: обход такой коллекции не заканчивается,
а запись в хранилище значения приводит к ошибке.

```правило
код: std.collection-self-insert
уровень: высокий
```

### 12.6. Возврат значения процедурой

Значение возвращает функция; `Возврат` со значением в процедуре — ошибка
проверки конфигурации.

```правило
код: std.procedure-returns-value
уровень: средний
```

### 12.7. Самоприсваивание

Переменной не присваивается её собственное значение: такая строка ничего
не делает и обычно означает потерянную правку.

```правило
код: std.self-assignment
уровень: средний
```

### 12.8. Временные файлы

Временный файл удаляется после использования, иначе каталог временных файлов
на сервере растёт до конца свободного места.

```правило
код: std.temp-file-not-deleted
уровень: низкий
```

### 12.9. Локализация текстов

Текст, который видит пользователь, оформляется через `НСтр()`, а подстановки —
через `СтрШаблон()`.

```правило
код: std.unlocalized-user-message
уровень: низкий
```

### 12.10. Полные права

Привилегированный общий модуль именуется с постфиксом `ПолныеПрава`,
а привилегированный режим включается и выключается парно.

```правило
код: sec.privileged-common-module
уровень: средний
```

```правило
код: sec.unbalanced-privileged-mode
уровень: высокий
```

### 12.11. Структура и читаемость

Модуль разделён областями, экспортные методы описаны, дублирующийся код
вынесен в общий модуль.

```правило
код: std.no-regions
уровень: средний
```

```правило
код: std.undocumented-export
уровень: низкий
```

```правило
код: arch.duplicate-code
уровень: средний
```

### 12.12. Динамическое исполнение кода

`Выполнить` и `Вычислить` со сформированной строкой — способ исполнить
на сервере что угодно.

```правило
код: sec.dynamic-execution
уровень: высокий
```
